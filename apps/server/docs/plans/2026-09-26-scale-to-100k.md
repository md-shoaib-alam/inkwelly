# Plan: comfortably handling 100k+ active users

**Written:** 2026-09-26 · **Status:** proposal, no code changed by this document
**Evidence base:** `docs/capacity-report-2026-09-26.md` (local) and `docs/capacity-local-vs-vps-2026-09-26.md` (VPS)

---

## 0. What "100k users" has to mean before you can plan for it

The phrase hides three different numbers, and the hardware you need differs by ~10× between them.

| Term | Meaning | This plan assumes |
|---|---|---|
| Registered | rows in `"User"` | 300,000 across all tenants |
| Active (DAU) | distinct users on a normal day | **100,000** |
| Peak concurrent | logged in and in-app at the same moment | **25% of DAU = 25,000** |
| Peak req/s | what the box actually feels | **~900–1,400/s**, see §2 |

**Why the ratio is 25% and not something smaller:** this is a school product. Everyone is in the building
between 07:45 and 08:30 IST, and the traffic is not flat — it is a cliff at the start of the day. A
consumer app might see 10% concurrency; a school roll-call app sees more, closer to the peak hour. If
you have a real number for one busy morning, replace this assumption — every figure below is linear in it.

**The one-line goal:** serve ~1,500 req/s sustained with p95 under 200 ms, ~25 sustained logins/s during
the 08:00 cliff, and survive one box dying. Today the honest ceiling is ~1,050 req/s on a box where that
number did not scale with a second process.

## 1. Measured today — what we're planning against

These were measured, not estimated:

| Fact | Number | Where |
|---|---|---|
| Authenticated req/s, 1 Bun process, 2 vCPU | ~1,050 | VPS sweep, flat from 10 → 320 VUs |
| HTTP-only req/s (route that returns 404) | ~3,100 | VPS |
| CPU cost per authenticated request | ~1.12 ms | VPS |
| CPU cost for a request that does nothing | ~0.30 ms | VPS |
| argon2id verify | ~215 ms CPU, ~64 MB RAM | local |
| Logins/s per core | ~4.6 | derived from the two rows above |
| RTT app → managed Postgres (same provider, private net) | 0.198 ms | VPS |
| RTT laptop → same Postgres (public) | 28.7 ms | local |
| Two Bun processes on one 2 vCPU box | **no throughput gain** | VPS |
| Raising the pg pool 20 → 60 → 100 | **286 → 261 → 253 req/s (worse)** | local |

The auth hot path per request is: `jwtVerify` → `sha256` → **1 Redis GET** (token denylist) → **1 `User`
SELECT** → compare `tokenIatMs < updatedAtMs`. That is ~0.82 ms of the 1.12 ms.

**What the gap between 0.30 ms and 1.12 ms means:** roughly three quarters of every request's cost is
things you could stop doing. That is the single biggest lever in this whole plan, and it is why §4 comes
before anything about buying servers.

## 2. The arithmetic that decides the hardware

| Load | Basis | Result |
|---|---|---|
| Read/poll traffic | 25,000 concurrent, and the today-view polls every 60 s | **~417 req/s from polling alone** |
| Everything else a concurrent user does | dashboards, lists, attendance marking ≈ 0.03 req/s each | ~750 req/s |
| **Total peak** | | **~1,150–1,400 req/s** |
| Logins in the 08:00 cliff | 100k DAU, 60% of them arriving inside a 60-min window, ~1 login/user/day | **~17/s sustained, ~35/s burst** |

Against the measured baseline: **~1.4× the req/s of one today-process, and ~4–8× its login rate.**
Reads are a sizing problem. **Login is the actual wall** — 35/s burst at 4.6/s per core is ~8 cores spent
doing nothing but hashing passwords, and they are needed at the exact minute everything else peaks.

That reframing matters, because it means a bigger box alone does not fix you. §5 and §6 attack login.

## 3. Where a "wall" is not a wall

- **Postgres is not the constraint.** Confirmed on the real topology; the local report's "database is the
  wall" conclusion is formally withdrawn. It will become a constraint through *volume per table* (§7), not
  through per-query speed.
- **The rate limiters are not a capacity limit** any more. They are a correctness risk in the other
  direction (they can lock out a school), addressed in Phase 0/1.
- **Connection pool size is not a lever.** Measured negative. Do not raise it again looking for throughput.
- **CPU, not RAM**, is the binding resource for the API. 7.8 GB was never close. argon2 is the only RAM
  spike worth respecting (64 MB per concurrent verify → 35 concurrent logins ≈ 2.2 GB of transient churn).

## Phase 1 — Get a truthful baseline (before spending money)

The VPS numbers have a known bias: k6 ran on the same 2-core box as the app, so every "this box caps at
N" is an *under*-estimate of the app. And `MODE=mix`, `MODE=login`, `MODE=write` never ran there at all.

- **P1.1** Rent the target-size box (4 vCPU / 8 GB is enough for this phase) **plus a separate cheap
  generator box**. Never load the box you are measuring.
- **P1.2** Re-run the VU sweep, then `MODE=mix`, `MODE=login`, `MODE=write` on the target box.
- **P1.3** Settle the one thing that stayed inferred: **why two processes did not scale.** Two commands,
  on their own box: `redis-benchmark -t get -c 20 -P 1 -q` and a raw `User` primary-key SELECT loop at
  concurrency 1/10/40/100. Until this is measured, Phase 2's "move Redis off" recommendation is a strong
  inference, not a fact.
- **P1.4** Check `maxmemory-policy` on whatever Redis production uses. **It must be `noeviction`.** If it
  is `allkeys-lru`, an eviction silently deletes token-denylist entries and login counters — a security

## Phase 2 — Topology: separate the three things fighting for CPU

Today one box holds the API, Redis and (in real operation) BullMQ workers, and they contend precisely at
08:00.

- **P2.1 Redis off the app box** — managed Redis in the same region, or its own 1 vCPU node. Co-located
  Redis costs ~0.5–0.75 core, which on a small box is the whole difference between "2 processes = 2×" and
  "2 processes = 1×". Do **not** stay on Upstash free tier for production: at ~200 req/s the token
  denylist alone is ~17M commands/day against a 500k/day allowance.
- **P2.2 Workers off the API box.** `START_WORKERS=false` in every measurement was deliberate; a real
  morning has BullMQ competing for the same cores. Give it the second app node.
- **P2.3 Watch the quiet-hours single-writer rule.** The 21:00–07:00 IST gating and the morning resume must
  run in exactly **one** process. Two schedulers = duplicate fan-out = double the notifications to parents.
  Same for anything that must be gated at *enqueue* time, since workers are paused overnight.
- **P2.4 Keep Postgres where it is.** 4 vCPU / 16 GB managed is right-sized; it is configured wrong (§7).

| Component | Where | Size |
|---|---|---|
| API (Bun ×2–3) | node A | 4 vCPU / 8 GB |
| BullMQ workers | node B | 2 vCPU / 4 GB |
| Redis (cache + denylist + BullMQ, `noeviction`) | node C or managed | 1 vCPU / 2 GB |
| Postgres | managed, unchanged node | 4 vCPU / 16 GB |

## Phase 3 — Make the limiters true across instances

Small, and it blocks Phase 6: the general rate-limit counter and the login fallback are **in-process maps**.
With 3 instances the effective limit is 3× what the config says, and a `redis.status !== 'ready'` fallback
means different instances disagree.

- **P3.1** Make Redis the only counter store for these paths; **fail closed** (reject) rather than falling
  back to a local map if Redis is down for the *login* limiter, and decide explicitly for the general one.
  The local fallback exists so a Redis outage can't disable brute-force protection — but on a multi-instance
  box it also means the protection is not the number you configured. Write the choice down either way.
- **P3.2** Key the general limiter per **tenant** as well as per IP, so one school's NAT address cannot spend
  another school's budget.

## Phase 4 — Cut the per-request cost (biggest multiplier)

Target: **1.12 ms → ~0.4 ms per request ⇒ ~1,050 → ~2,500 req/s per core**, from work removal, not hardware.

- **P4.1 Cache the auth tuple in-process.** Key `jti`, value `{updatedAt, isActive, tenantId, role, name}`,
  TTL 3–5 s. Kills the per-request `User` SELECT.
  **The trade-off is a security one and it is yours:** deactivating a user or rotating their password takes
  up to 5 s to take effect instead of being instant. Say the number you accept.
- **P4.2 Stop the per-request Redis GET.** Check the denylist only where it must be fresh (refresh,
  privileged writes), or keep a local set of revoked `jti`s with a TTL equal to the token lifetime. Same
  staleness question as P4.1.
- **P4.3 Trim the SELECT shape.** If P4.1 is refused for staleness reasons, at minimum select only the five
  columns and confirm the query is the primary-key hit and not the `email` unique index + join.
- **P4.4 Confirm `getPoolStats()` is not called per request.** It now runs a real `pg_stat_activity` query.

**Measure before and after, same script, and revert anything inside noise.** This phase is exactly where a
"neutral" change must not be kept.

## Phase 5 — The 60-second poll (the fan-out wall)

~417 req/s at 25k concurrent is spent asking "anything new?" and mostly getting "no".

**The constraint you cannot code around:** changing the interval is an **app change**, and app changes need
a store release. So prefer server-side wins that need no release:

- **P5.1 Conditional GET / ETag on the "today" endpoints.** Unchanged data answers `304` with no body and,
  more importantly, no serialization. Cheap, invisible to old app versions that ignore it, and the win is
  immediate for the expensive part.
- **P5.2 If you can ship an app release later, widen the interval adaptively** (60 s → 120 s when nothing
  has changed for a while, back to 15 s on interaction). Do this only knowing **the 60 s today-poll and the
  pure-view mobile tabs were deliberate design decisions** — see the QR-attendance decisions note — so this
  item needs a product sign-off, not just a perf one.
- **P5.3 Long-poll or SSE** as the eventual replacement; the notification bell already uses
  FCM-triggered refresh plus a cached `/count` poll, so the pattern exists.

**Anti-goal:** do **not** answer the poll by adding a Redis cache of per-user "today" data. Per-user keys are
not shared, the Postgres indexed point read is effectively free, and Upstash/Redis commands are your scarce
budget. Cache only tenant-wide shared keys.

## Phase 6 — Login: stop paying argon2 on the request thread

The wall in §2. ~8 cores of hashing at 100k DAU is not a sizing answer, it's a design answer.

- **P6.1 Log in less often.** Check the real tokens-per-user-per-day. With a 7-day refresh token and silent
  refresh, 100k DAU should be far below 100k logins/day; if the clients re-login every morning you are
  paying argon2 for nothing. **Measure this first — it may be the cheapest 5× in the whole plan.**
- **P6.2 Move hashing off the API event loop** into a dedicated worker pool or separate process, so a
  08:00 stampede cannot starve reads. 64 MB per concurrent verify also means a burst is a memory event, not
  just a CPU one.
- **P6.3 Client-side jitter** on automatic retries, so a network blip does not become a synchronised
  re-login storm.
- **P6.4 `memoryCost` is a security decision, made deliberately and written down.** Lowering it buys cores
  by weakening the hash. Do not let it be a side effect of a capacity panic.
- **P6.5 Escalate to friction, not to a block.** After N failures for one *account*, require a captcha;
  never block an *address* hard, because that is the school-outage bug just fixed.

## Phase 7 — Postgres: correctness now, partitioning before it's urgent

- **P7.1 `Attendance.date` / `month` are TEXT with two formats already in the column** (`'2025-04-01'` and
  `'2026-06-20T00:00:00.000Z'`). Whether a screen returns rows currently depends on which write created
  them. At 100k users that is wrong answers at scale, and it gets harder to fix the longer it waits because
  the table only grows. **This is the highest-priority item in this phase and it is not a performance
  item.** Needs a migration + backfill plan with a rollback, on your go-ahead.
- **P7.2 Partition `Attendance`** (by month, or by tenant+year) as part of the same migration. 1.08M rows
  is one school-year for one school; the same day across 100k users is two orders of magnitude larger, and
  13 indexes on a table that big is a write cliff, not a read problem.
- **P7.3 Index diet** — after P7.1, read `pg_stat_user_indexes` on the real database and drop what is
  unread. Today: 404 MB of index against a 147 MB heap. Every insert pays all 13.
- **P7.4 `shared_buffers` 128 MB → ~4 GB**, plus `effective_cache_size ≈ 10 GB` and `wal_compression=on`.
  **Needs a restart.** Untouched so far because I won't restart your database without you.
- **P7.5 `pg_stat_statements`** so the next round of this document is built on real query timings.
- **P7.6 PgBouncer** only if you move to many instances; then decide `prepare: true` vs transaction mode
  explicitly — they fight, and the current pool of 20 is not the problem so don't add a proxy to fix it.

## Phase 8 — Run more than one instance (only after Phases 2, 3, 4)

Deliberately last. Multi-processing before P3 is a silent limit-multiplier, and before P2 it buys nothing.

- **P8.1** 2–3 Bun processes behind nginx/Caddy on `127.0.0.1`, then the box is actually used.
- **P8.2** Graceful shutdown + connection drain so a deploy is not a 502 window.
- **P8.3** Keep per-instance state honest: the P4.1 auth cache is per-instance, which is fine at a 3–5 s TTL
  but must not be relied on for instant revocation.
- **P8.4** Single-writer jobs (P2.3) before the second instance starts, not after.

---

## Phase 9 — Observability and resilience (do this alongside, not "later")

Today production has no APM, no perf monitoring, and no verified restore path. At 100k users a lost database
is not an outage, it is the end of the company.

- **P9.1** Dashboards + alerts on: p95 latency per route, req/s per process, CPU per process, **login/s**,
  429 rate (a spike means a school is being locked out — the bug class just fixed), pool `blocked`/
  `idleInTransaction` (now real), Redis latency, BullMQ depth, poll 304-hit ratio.
- **P9.2** Alert thresholds derived from §2's table, not invented.
- **P9.3** **Backups: schedule + a restore drill with a timestamp.** Not "backups exist".
- **P9.4** SLO: p95 < 200 ms at 1,500 req/s; login p95 < 1 s at 25/s; zero per-IP lockouts of a whole tenant.
- **P9.5** Run the two microbenchmarks from P1.3 to close the Redis-vs-Postgres question.

## Explicitly NOT doing

| Temptation | Why not |
|---|---|
| Bigger VPS first | Login and per-request CPU are the walls; a bigger box makes the *current* failure arrive faster (in-process limiters multiply per instance) |
| Redis-cache per-user pages | per-user keys aren't shared, the Postgres point read is free, Redis commands are the scarce budget |
| Raise `max` on the pg pool | measured 286 → 253 req/s. Reverted, and don't revisit |
| Rewrite in Go / drop Drizzle | the cost is work being done, not the language doing it — 0.82 ms of 1.12 ms is removable in place |
| Shard Postgres | 100k DAU is a partitioning problem, not a sharding one |
| Turn off the 60 s poll in the app | needs a store release, and the today-poll was a deliberate product decision |
| Hard-block noisy IPs | that is the outage just removed; block accounts, add friction, never close a building |

## What I could not measure (so the plan does not pretend)

1. `MODE=mix`, `MODE=login`, `MODE=write` were **never run** on the VPS. §2's req/s is arithmetic on a
   measured read ceiling plus a locally measured request-per-user rate.
2. **Which shared resource blocked two processes** (Redis vs Postgres vs softirq) is a strong inference
   from CPU accounting, not a proven fact. P1.3 settles it.
3. Load generator shared the measured box ⇒ ceilings are under-estimates of the app.
4. TLS, HTTP/2, reverse proxy, real mobile networks, multi-tenant contention (all traffic hit one tenant),
   FCM sends and any soak/leak test: untested.
5. Real tokens-per-user-per-day is unknown — which makes **P6.1 potentially the largest unclaimed win here**
   and also the cheapest to check.
